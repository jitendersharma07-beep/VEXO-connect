## 1. Design commitments (why the shapes look like this)

1. **One pricing evaluator.** A phone order's money is computed by the existing
   `recomputeOrder()` in `backend/src/lib/orders.js` — the same function the till
   uses. This module never computes totals. (`LANE-BRIEF §3`.)
2. **The Order is created at submission, not at acceptance.** A phone order is a
   real `Order` in the routed store from the moment it is submitted, so pricing,
   tax, KOT, payment and refund all reuse the existing lifecycle unchanged. The
   `PhoneOrder` row is a *sidecar* carrying customer, address, fulfilment,
   scheduling, routing and acceptance. There is no second item store and no
   second money path.
3. **`Order.channel` is NOT added.** The orders lane owns `Order.channel`,
   provider and external-ref (`LANE-BRIEF §3`). Phone origin is recorded on the
   sidecar. See §10 conflict C-1.
4. **`OrderType` gains no value.** Pickup and delivery are both `TAKEAWAY` at the
   `Order` level; the real fulfilment mode lives on `PhoneOrder.fulfilment`.
   See §10 conflict C-2.
5. **Issued invoices never move.** Reassignment is refused once
   `Order.invoiceNumber` is non-null. Corrections are new rows, never mutation.
6. **The delivery charge is QUOTED, not billed** — see §12. It is returned
   beside the order total, never inside it, until C-6 is answered.

## 2. Mount point and common conventions

All routes are mounted under **`/api/phone-orders`**.

Every route runs `requirePosAuth`, `resolveCompanyScope`, `deviceContext`, then
role and licence gates. Tenant scope is always taken from
`req.companyScope.id` — **never** from the body.

Success envelopes are the existing style: `{ "<resource>": {...} }` or
`{ "<resource>s": [...] }`. Errors are the existing `AppError` shape:

```json
{ "error": { "code": "POS_BAD_REQUEST", "message": "…", "field": "pincode" } }
```

Money is rupees as a JSON number with 2 decimals, matching the rest of the API.
All arithmetic server-side is integer paise via `lib/money.js`.

Times are ISO-8601 UTC. Business days are IST (`istDateOf`, UTC+05:30).

## 3. Permissions and entitlement

Action keys use the `phone.` prefix and are exported from **one** map in this
lane, `backend/src/lib/phoneOrders.js`:

| Action | Scope | Roles today |
|---|---|---|
| `phone.customer.read` | COMPANY | CUSTOMER_OWNER, BRANCH_MANAGER |
| `phone.customer.write` | COMPANY | CUSTOMER_OWNER, BRANCH_MANAGER |
| `phone.order.read` | COMPANY | CUSTOMER_OWNER, BRANCH_MANAGER |
| `phone.order.create` | COMPANY | CUSTOMER_OWNER, BRANCH_MANAGER |
| `phone.order.accept` | STORE | CUSTOMER_OWNER, BRANCH_MANAGER |
| `phone.order.reassign` | COMPANY | CUSTOMER_OWNER |

Rules that hold regardless of role:

- **Branch-pinned roles** (`BRANCH_MANAGER`, `CASHIER`) may only act on
  `req.user.branchId`. A branch manager can accept or reject for **their own
  store only**, and sees only their own store's phone orders.
- `CUSTOMER_OWNER` acts on any branch of their own company.
- `POS_SUPER_ADMIN` has **no** routine business rights here — it cannot create,
  accept or reassign a phone order. It is not a tenant operator.
- Customer phone and address data is returned **only** to callers holding
  `phone.customer.read`. (`A§3 VC-104`: "phone/address data visible only to
  authorized staff".)

**Entitlement.** Two module keys are exported and every router is marked:

```js
export const MODULE_KEY = 'PHONE_ORDERS';       // Pro
export const HQ_ROUTING_KEY = 'HQ_ROUTING';     // Enterprise
// ENTITLEMENT(PHONE_ORDERS)
```

No module/tier entitlement mechanism exists yet — `LicensePlan` is only
`FREE_TRIAL | SINGLE_STORE | MULTI_STORE` and `LicenseAddonKind` is only
`ADDITIONAL_BRANCH`. `requireModule(key)` belongs to the firstlogin lane.

Until it lands, **HQ routing is gated conservatively**: routing an order to a
store other than the operator's own requires `LicensePlan = MULTI_STORE`. On
`SINGLE_STORE` or `FREE_TRIAL`, cross-store routing returns
`POS_HQ_ROUTING_NOT_ENTITLED` (403). This is an honest proxy — central routing
is inherently multi-store — and it is marked `// INTEGRATION(firstlogin)` so it
swaps out mechanically. See §10 conflict C-3.

## 4. State machine

```
                      POST /api/phone-orders
                               |
                               v
                         [ SUBMITTED ]  <-- Order exists, status OPEN, in routedBranch
                          /    |     \
              accept     /     |      \     reject
                        v      |       v
                 [ ACCEPTED ]  |  [ REJECTED ]
                        |      |
                        |      | reassign (SUBMITTED only, invoiceNumber must be null)
                        |      +--> recomputeOrder() -> stays SUBMITTED, new routedBranch
                        v
              normal till lifecycle: KOT -> bill -> pay -> close
                        |
                        v
                  [ CANCELLED ]  (only while no payment exists)
```

| State | Meaning | Order.status |
|---|---|---|
| `SUBMITTED` | Routed to exactly one store, awaiting that store's decision | `OPEN` |
| `ACCEPTED` | Exactly one store owns it; attribution frozen | `OPEN` |
| `REJECTED` | Store refused; needs reassignment or cancellation | `OPEN` |
| `CANCELLED` | **Not reachable yet — do not build a filter chip for it.** The enum carries the value, but no route sets it: cancelling an order that may already hold money needs refund/void rules that wait on C-6 (§12). `GET /api/phone-orders?status=CANCELLED` is rejected as an unknown filter rather than returning an empty list | — |

**Exactly one accepting store** is enforced by a conditional `UPDATE` inside a
transaction with `SELECT … FOR UPDATE` on the `PhoneOrder` row, guarded on
`status = 'SUBMITTED' AND acceptedBranchId IS NULL`. The loser of a race gets
`409 POS_PHONE_ORDER_ALREADY_DECIDED` and **no** second Order or KOT is created,
because the Order was created once at submission.

## 5. Endpoints

### 5.1 `GET /api/phone-orders/customers?q=<term>&limit=<n>`

Tenant-scoped customer search. `q` matches name (contains, case-insensitive) or
phone (prefix). Minimum 3 characters. `limit` default 20, max 50.

**200**
```json
{ "customers": [
  { "id": "ckc1", "name": "Anita Rao", "phone": "+919876500011",
    "addressCount": 2, "lastOrderAt": "2026-09-20T11:05:00.000Z" }
] }
```
Never returns customers of another company. `q` under 3 chars -> `400` field `q`.

### 5.2 `POST /api/phone-orders/customers`
```json
{ "name": "Anita Rao", "phone": "+919876500011", "email": null, "note": null }
```
**201** `{ "customer": { … } }`. Phone is unique per company; a duplicate returns
**409 `POS_CONFLICT`** with the existing customer id in `error.details.customerId`
so the screen can offer "open the existing customer" instead of failing.

### 5.3 `GET /api/phone-orders/customers/:id`

**200**
```json
{ "customer": {
    "id": "ckc1", "name": "Anita Rao", "phone": "+919876500011",
    "addresses": [
      { "id": "cka1", "label": "Home", "line1": "12 Church St", "line2": null,
        "landmark": "opp. bakery", "city": "Bengaluru", "pincode": "560001",
        "isDefault": true, "archivedAt": null }
    ],
    "history": [
      { "orderId": "cko9", "invoiceNumber": "BSC-CP/26-27/00042",
        "branchId": "ckb1", "branchName": "Church Street",
        "total": 480.00, "status": "CLOSED", "billedAt": "2026-09-20T11:05:00.000Z",
        "fulfilment": "DELIVERY" }
    ] } }
```

`history` is **permitted history**: for `CUSTOMER_OWNER`, every store of the
company; for a branch-pinned role, **only orders from their own store**. The
list is capped at 20 most recent.

### 5.4 `POST /api/phone-orders/customers/:id/addresses`
```json
{ "label": "Home", "line1": "12 Church St", "line2": null,
  "landmark": "opp. bakery", "city": "Bengaluru", "pincode": "560001",
  "isDefault": true }
```
**201** `{ "address": { … } }`. `pincode` is exactly 6 digits. Setting
`isDefault: true` clears the previous default in the same transaction.

### 5.5 `PATCH /api/phone-orders/customers/:id/addresses/:addressId`

Same body, all fields optional, plus `"archived": true` to retire an address.
An archived address cannot be used for a new order (**400**, field `addressId`).

### 5.6 `POST /api/phone-orders/branch-options`

The branch selector's data source. Returns **every** candidate store with an
explicit verdict — the UI must show why a store is unavailable, not hide it.

```json
{ "fulfilment": "DELIVERY",
  "addressId": "cka1",
  "scheduledFor": "2026-09-24T14:30:00.000Z",
  "items": [ { "productId": "ckp1", "variantId": null, "qty": 2 } ] }
```

`fulfilment` is `PICKUP | DELIVERY`. For `DELIVERY`, `addressId` is required.
For `PICKUP`, it is ignored. `scheduledFor` null means "as soon as possible".
`items` is optional; when present, menu availability is evaluated against it.

**200**
```json
{ "options": [
  { "branchId": "ckb1", "branchName": "Church Street", "branchCode": "BSC-CP",
    "available": true,
    "deliveryCharge": 40.00,
    "minOrder": 200.00,
    "hours": { "opensAt": "09:00", "closesAt": "23:00", "openAtFulfilment": true },
    "capacity": { "slotMinutes": 15, "maxOrdersPerSlot": 6, "booked": 2 },
    "unavailableReasons": [] },

  { "branchId": "ckb2", "branchName": "Indiranagar", "branchCode": "BSC-IN",
    "available": false,
    "deliveryCharge": null, "minOrder": null,
    "hours": { "opensAt": "11:00", "closesAt": "22:00", "openAtFulfilment": false },
    "capacity": { "slotMinutes": 15, "maxOrdersPerSlot": 6, "booked": 6 },
    "unavailableReasons": [
      { "code": "NOT_SERVICEABLE", "message": "Does not deliver to 560001" },
      { "code": "CLOSED_AT_FULFILMENT", "message": "Closed at 14:30 on Thursday" }
    ] } ] }
```

**`unavailableReasons[].code` is a closed set** — the UI may key copy off it:

| Code | Meaning |
|---|---|
| `NOT_SERVICEABLE` | No service area covers the address pincode |
| `CLOSED_AT_FULFILMENT` | Store closed at the requested time |
| `AT_CAPACITY` | Prep slot for the fulfilment time is full |
| `MENU_UNAVAILABLE` | One or more requested items are not on this store's menu |
| `BELOW_MIN_ORDER` | Basket is under the store's delivery minimum |
| `BRANCH_INACTIVE` | `Branch.status != ACTIVE` |
| `NOT_ENTITLED` | Cross-store routing without `MULTI_STORE` |

A store with `available: true` has an **empty** `unavailableReasons`.
A store may carry several reasons at once; all are returned, never just the first.

### 5.7 `POST /api/phone-orders` — submit

**Idempotent.** `idempotencyKey` is required, 8–64 chars, stable per submission
attempt (the UI generates it once when the operator opens the form and reuses it
across retries and double-clicks).

```json
{ "idempotencyKey": "po-3f9c1a2b-7d4e",
  "customerId": "ckc1",
  "addressId": "cka1",
  "fulfilment": "DELIVERY",
  "branchId": "ckb1",
  "scheduledFor": "2026-09-24T14:30:00.000Z",
  "note": "ring the bell twice",
  "items": [ { "productId": "ckp1", "variantId": null, "qty": 2 } ] }
```

Server re-validates the chosen `branchId` against §5.6 **at submission time** and
refuses if it is no longer available — the operator's screen may be stale.

**201**
```json
{ "phoneOrder": {
    "id": "ckpo1", "status": "SUBMITTED",
    "reference": "PH-000123",
    "customerId": "ckc1", "addressId": "cka1",
    "fulfilment": "DELIVERY",
    "scheduledFor": "2026-09-24T14:30:00.000Z",
    "routedBranchId": "ckb1", "acceptedBranchId": null,
    "operatorId": "cku7", "operatorName": "Priya N",
    "deliveryCharge": 40.00,
    "deliveryChargeTreatment": "UNRESOLVED_POST_TAX_FALLBACK",
    "deliverySupplier": "UNRESOLVED",
    "deliveryChargeBillable": false,
    "order": { "id": "cko9", "status": "OPEN", "subtotal": 400.00,
               "taxAmount": 20.00, "total": 420.00, "invoiceNumber": null },
    "payableQuote": 460.00 } }
```

**Read these three numbers carefully — this changed in `1.1.0-draft`.**

- `order.total` is the authoritative order money, written only by
  `recomputeOrder()`. It is **food and tax only**. It does **not** include the
  delivery charge.
- `deliveryCharge` is quoted separately and is **not** in any tax base.
- `payableQuote` = `order.total + deliveryCharge`. It is what the operator reads
  to the caller. It is a **quote, not a bill**: while
  `deliveryChargeBillable` is `false`, no invoice may present the delivery
  charge as part of the restaurant's supply.

W2: show `payableQuote` as the amount to collect, and show `deliveryCharge` as
its own line. Do **not** add the two yourself and do not display `order.total`
as the payable. Rationale in §12.

**Replaying the same `idempotencyKey`** returns **200** (not 201) with the
identical body. No second Order, no second KOT. A *different* body under a
previously used key returns **409 `POS_IDEMPOTENCY_KEY_REUSED`**.

### 5.8 `POST /api/phone-orders/:id/accept`

Body: `{}` — the accepting store is the caller's store, taken from the token,
never the body.

**200** `{ "phoneOrder": { …, "status": "ACCEPTED", "acceptedBranchId": "ckb1",
"acceptedAt": "…", "acceptedById": "cku4" } }`

**409 `POS_PHONE_ORDER_ALREADY_DECIDED`** if it is not `SUBMITTED` — this is what
the loser of a concurrent accept receives.
**403** if the caller's store is not `routedBranchId`.

### 5.9 `POST /api/phone-orders/:id/reject`
```json
{ "reason": "kitchen at capacity until 16:00" }
```
`reason` 3–200 chars, required. **200** with `status: "REJECTED"`.
Same store check and same 409 as accept.

### 5.10 `POST /api/phone-orders/:id/reassign`
```json
{ "branchId": "ckb2", "reason": "original store rejected" }
```

Allowed from `SUBMITTED` or `REJECTED`. Requires `phone.order.reassign`.

- Refused **409 `POS_INVOICE_ISSUED`** when `Order.invoiceNumber` is non-null.
  An issued invoice never moves store. (`A§3 VC-104`.)
- Refused **409 `POS_CONFLICT`** when a payment already exists.
- The target store is re-validated against §5.6, and refused **409
  `POS_BRANCH_UNAVAILABLE`** if it fails — including **because the destination
  slot is full**. Since 09-25 a transfer occupies a place in the slot it
  ARRIVES in (C-5), so a move into a full store is refused where it previously
  succeeded. The order does not move: it stays live at its source store, in its
  original slot, and `unavailableReasons` carries the capacity text.
- **Pricing and tax are recomputed** for the new store before the response
  returns, via `recomputeOrder()`. The response carries the new totals, and the
  UI must show them as a changed price, not reuse the old summary.
- Writes a `PhoneOrderEvent` and an audit row with both store ids.
- **`priceChanged` means the caller's payable moved** — `payableQuote` before vs
  after, which is order total + tax + the new store's delivery charge. It is the
  operator's cue to re-read the quote before hanging up.

  It is deliberately *not* limited to `Order.total`/`taxAmount`. While the
  catalogue is company-wide and each line's price and tax rate are snapshotted at
  submit, those two figures **cannot** move on a reassignment, so a flag watching
  only them would be false on every move ever made — including the ones that cost
  the caller more. Corrected 09-24 (D-1); clients should not re-derive the drift
  from `payableQuote` themselves.

**200** `{ "phoneOrder": { …, "status": "SUBMITTED", "routedBranchId": "ckb2",
"order": { …recomputed totals… } }, "priceChanged": true }`

### 5.11 `GET /api/phone-orders/:id` and `GET /api/phone-orders?status=&branchId=&limit=`

List is scoped: branch-pinned roles see only their own store's orders.
`status` accepts a comma-separated subset of `SUBMITTED`, `ACCEPTED`,
`REJECTED`. `CANCELLED` is **not** accepted — see §4.

## 6. Error codes (complete set for this module)

| HTTP | `code` | When |
|---|---|---|
| 400 | `POS_BAD_REQUEST` | validation; `field` names the offender |
| 401 | `POS_UNAUTHENTICATED` | no/invalid session |
| 403 | `POS_FORBIDDEN` | role or store scope refuses |
| 403 | `POS_HQ_ROUTING_NOT_ENTITLED` | cross-store routing without `MULTI_STORE` |
| 403 | `POS_LICENSE_EXPIRED` / `_SUSPENDED` / `_MISSING` | existing licence gate |
| 404 | `POS_NOT_FOUND` | customer / address / phone order / branch not in tenant |
| 409 | `POS_CONFLICT` | duplicate customer phone; payment exists |
| 409 | `POS_PHONE_ORDER_ALREADY_DECIDED` | accept/reject race loser |
| 409 | `POS_IDEMPOTENCY_KEY_REUSED` | same key, different body |
| 409 | `POS_INVOICE_ISSUED` | reassignment after an invoice was issued |
| 409 | `POS_BRANCH_UNAVAILABLE` | chosen store failed re-validation — **at submit or at reassign** |

`POS_BRANCH_UNAVAILABLE` carries the same `unavailableReasons` array as §5.6 in
`error.details.unavailableReasons`, so the screen can explain the refusal
without a second round trip.

It is raised from three places, and a screen that only handles the submit case
will show the wrong copy for the other two: `POST /phone-orders` (§5.7) and
`POST /phone-orders/:id/reassign` (§5.10) both re-run serviceability, and
`reserveSlot` raises it from inside either transaction when the slot is full —
which, since 09-25, includes the destination slot of a transfer (see C-5). A
refusal at reassign means the order did **not** move; it is still live at its
source store, in its original slot.

**Refusal precedence on `reassign`, because it changes the message you show.**
The state guard is evaluated before the invoice guard. An **ACCEPTED** order
returns `POS_PHONE_ORDER_ALREADY_DECIDED` even if its invoice has also been
issued; `POS_INVOICE_ISSUED` is what a **SUBMITTED or REJECTED** order with an
issued invoice returns. Both refuse, and in both cases the order does not move —
but do not key "an invoice was issued" copy off the accepted case.

The full order on `reassign` is **state → invoice → payment → destination**:
`POS_PHONE_ORDER_ALREADY_DECIDED` (not SUBMITTED/REJECTED), then
`POS_INVOICE_ISSUED`, then `POS_CONFLICT` (a payment exists), and only then
`POS_BRANCH_UNAVAILABLE`. So capacity is the **last** thing checked and the
first thing an operator can do something about — the other three are permanent
for that order, a full slot is not. It is also checked twice: once outside the
transaction against §5.6 (the forecast) and once inside it under the advisory
lock (the binding one, C-5), so a transfer can pass the first and still be
refused by the second when another till takes the last place in between. Both
raise the same code, and in neither case does the order move.

## 10. Spec conflicts and assumptions (owner input wanted)

| # | Item | Resolution taken |
|---|---|---|
| C-1 | `A§3 VC-104` wants phone orders distinguishable as a channel, but `LANE-BRIEF §3` gives `Order.channel` to the orders lane | Channel is **not** added. Origin lives on `PhoneOrder`. When the orders lane lands `Order.channel`, integration sets it to `PHONE` from the sidecar — one mechanical migration, no data loss |
| C-2 | Pickup/delivery have no `OrderType` value | Both stored as `TAKEAWAY`; real mode on `PhoneOrder.fulfilment`. Not adding a value to a shared enum another lane owns |
| C-3 | "Enterprise HQ-routing entitlement" has no mechanism to enforce | Conservative proxy: cross-store routing requires `MULTI_STORE`. Marked `// INTEGRATION(firstlogin)` |
| C-4 | Serviceability: spec says "unsupported addresses … blocked or require an authorized alternative" but does not define serviceability | Pincode-based `BranchServiceArea`. Deterministic, no geo/maps dependency, testable. Radius/polygon is a later change behind the same API |
| C-5 | "Preparation capacity" is undefined | Orders-per-slot per store (`slotMinutes`, `maxOrdersPerSlot`). Counted over live (`SUBMITTED`/`ACCEPTED`) phone orders falling in the same slot: a scheduled order by its `scheduledFor`, an **ASAP order by the slot it was taken in** (`createdAt`), and an **ASAP order moved here by the slot it ARRIVED in** — the `at` of the latest `REASSIGNED` event into the current store. Slots are half-open `[start, end)`: an order anchored exactly on a boundary belongs to the slot opening, not the one closing. ## 12. C-6 — the delivery charge, and why it is not in the total

**Status: OPEN. Owner input required. The behaviour below is a labelled
temporary fallback, not a decision.**

### What has to be established

Two facts, neither of which this project has settled:

1. **Who supplies the delivery service** — the restaurant itself, or a third
   party (a platform/aggregator or an independent rider).
2. **Whether the charge is separate consideration** for a distinct supply, or
   part of a composite supply of restaurant service.

### Why the answers point opposite ways

| If | Then the charge |
|---|---|
| Composite supply, restaurant is the supplier | belongs **inside** the order's tax base, at the restaurant rate |
| Separate consideration, third-party supplier | is **not the restaurant's supply at all** and must never appear in this invoice |

A post-tax add-on is neither of those. It is merely the only position that can
still move to either one.

### Why it is not folded into `Order.total` today

`recomputeOrder()` builds `subtotal`, `taxAmount` and `total` purely from
`OrderItem` rows, and `OrderItem.productId` is a required FK to `Product`.
Folding the charge in would mean minting a synthetic "Delivery" product — which
would put delivery revenue into food sales and straight into VC-105's
per-item margin analysis as if it were a menu item.

And the decisive reason: **issued invoices are immutable.** If C-6 resolves to
separate consideration by a third party, an invoice that already absorbed the
charge into the restaurant's tax base cannot be corrected, only credited. The
reversible choice is to keep it out until the answer is known.

### The fallback, precisely

- `PhoneOrder.deliveryCharge` holds the quoted amount.
- `PhoneOrder.deliverySupplier` = `UNRESOLVED` (`RESTAURANT` | `THIRD_PARTY`).
- `PhoneOrder.deliveryChargeTreatment` = `UNRESOLVED_POST_TAX_FALLBACK`
  (`COMPOSITE_SUPPLY` | `SEPARATE_CONSIDERATION`).
- `Order.total` never sees it. `Order.taxAmount` never sees it.
- The API reports `deliveryChargeBillable: false` while the treatment is
  unresolved.

Recording the unknown as **columns** rather than as a comment is deliberate: when
C-6 is answered, existing rows can be backfilled to the decided value and the
change is a data migration plus one branch in the quote builder — not a schema
change, and not a reinterpretation of money that was already billed.

### What closing C-6 will require

An answer to both questions in the first subsection, plus, if
`COMPOSITE_SUPPLY`, the rate to apply. Until then this lane does not bill a
delivery charge, and no evidence from this lane should be read as claiming it
does.
